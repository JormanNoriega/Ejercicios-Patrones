\begin{abstract}
Este informe explica los cinco principios SOLID mediante ejemplos en Java.
Cada ejemplo presenta el problema original y una solución basada en una
abstracción sencilla.
\end{abstract}

\section{Introducción}
SOLID reúne cinco principios para diseñar programas orientados a objetos más
fáciles de mantener, extender y probar. No son reglas para crear más clases sin
motivo: ayudan a separar responsabilidades y a controlar las dependencias.

El proyecto se compila directamente con Java 11. Los importes del ejercicio de
pedidos se representan con \texttt{BigDecimal}, apropiado para valores
monetarios.

\section{S: Responsabilidad única}
Una clase debe tener una sola responsabilidad y una sola razón para cambiar.
En el ejemplo incorrecto, \texttt{PedidoIncorrecto} mezcla datos, cálculo y
persistencia. La solución separa esas tareas: \texttt{Pedido} mantiene sus
productos, \texttt{CalculadoraPedido} calcula el total y
\texttt{PedidoRepository} se ocupa de guardar.

\begin{lstlisting}
Pedido pedido = new Pedido();
pedido.agregarProducto(new Producto("Cuaderno", new BigDecimal("10000")));
BigDecimal total = new CalculadoraPedido().calcularTotal(pedido);
new PedidoRepository().guardar(pedido);
\end{lstlisting}

Si cambia la forma de guardar, no es necesario modificar el modelo del pedido.

\section{O: Abierto/cerrado}
Una clase debe estar abierta para extenderse, pero cerrada para modificarse.
El ejemplo incorrecto usa una cadena y condicionales para decidir el tipo de
pago. Cada nuevo método obliga a modificar la función.

La solución define \texttt{MetodoPago} y hace que \texttt{ProcesadorPago}
dependa de esa interfaz:

\begin{lstlisting}
public class ProcesadorPago {
    private final MetodoPago metodoPago;

    public ProcesadorPago(MetodoPago metodoPago) {
        this.metodoPago = metodoPago;
    }

    public void procesar(double valor) {
        metodoPago.pagar(valor);
    }
}
\end{lstlisting}

Se pueden añadir \texttt{TarjetaPago}, \texttt{PaypalPago}, \texttt{NequiPago}
u otra implementación sin modificar el procesador.

\section{L: Sustitución de Liskov}
Una subclase debe poder utilizarse donde se espera su clase padre sin romper el
contrato. En el ejemplo incorrecto, el empleado de medio tiempo lanza una
excepción al calcular su salario.

En la solución, todos los tipos implementan la operación heredada de forma
válida:

\begin{lstlisting}
abstract class Empleado {
    public abstract double calcularSalario();
}

class EmpleadoMedioTiempo extends Empleado {
    public double calcularSalario() { return 1000000; }
}
\end{lstlisting}

También se incluye \texttt{EmpleadoPorComision}. Una lista de
\texttt{Empleado} puede contener los tres tipos y calcular sus salarios sin
conocer sus detalles.

\section{I: Segregación de interfaces}
Una clase no debe estar obligada a implementar métodos que no necesita. La
interfaz incorrecta \texttt{TrabajadorIncorrecto} obliga al robot a comer y
descansar.

La solución divide el contrato en \texttt{Trabajable}, \texttt{Comible} y
\texttt{Descansable}. El empleado implementa las tres, mientras que el robot
solo implementa \texttt{Trabajable}:

\begin{lstlisting}
class Robot implements Trabajable {
    public void trabajar() {
        System.out.println("El robot esta trabajando");
    }
}
\end{lstlisting}

El programa utiliza métodos que reciben únicamente la capacidad requerida,
como el método \texttt{asignarTrabajo}. Esto evita que
el robot no dependa de las otras interfaces.

\section{D: Inversión de dependencias}
Las clases de alto nivel deben depender de abstracciones, no de detalles
concretos. En el ejemplo incorrecto, \texttt{PedidoService} crea directamente
un \texttt{EmailNotificador}.

La solución recibe un \texttt{Notificador} por el constructor:

\begin{lstlisting}
public PedidoService(Notificador notificador) {
    this.notificador = Objects.requireNonNull(
        notificador, "El notificador es obligatorio");
}
\end{lstlisting}

El mismo servicio funciona con correo, WhatsApp u otro canal sin modificar el
servicio.

\section{Conclusión}
Los cinco ejemplos muestran que SOLID mejora la mantenibilidad cuando se aplica
a problemas concretos: separar el pedido de su cálculo, extender pagos mediante
interfaces, respetar contratos de herencia, dividir interfaces grandes e
inyectar dependencias.
